# 2026.288.1538 — feat(crabbox): the provider and firecracker-config surface reaches the CLI, proven in-venue

## Summary

**Supersedes #8**, whose two blocks this PR fixes: #8 named the R10 consumer beds while stating the bed was not
run, and pasted its R5 sweep as an annotation rather than as raw output. This PR carries the bed and the pin, plus
the schema and wiring the bed proved were missing, the raw sweep, and a green run.

Makes the `crabbox:` check verb able to express the Firecracker provider's own configuration surface, and proves
the provider selection reaches the CLI.

- **`schema/crabbox.cue`** gains `target?: string @go(Target)` and the **open** `firecracker?: {...} @go(Firecracker)`
  block. The block is deliberately open because the provider's key set is its own surface: a closed copy here would
  drift the moment upstream adds a key (R2).
- **`params/cue_types_gen.go`** is regenerated by `charly candy params plugin-crabbox` - `Target string` and
  `Firecracker map[string]any`. Go is generated, never hand-transcribed.
- **`methods.go`** appends `--target <os>` and `--firecracker-<key> <value>` (keys sorted) in `resolveCLICall`,
  under the **same measured allowlist** that already governs `--provider` - a method only receives a flag its CLI
  command defines.
- **`plugin_test.go`** gains the new struct fields plus three cases: `doctor --target linux`, `doctor
  --firecracker-binary firecracker`, and the `providers` **negative boundary** that must grow neither. The last one
  fails without the change.

Two steps are removed: they asserted the passthrough through `crabbox doctor`, whose exit code reports the
**venue's readiness**, not the passthrough. See "How tested".

The diff also touches **`README.md`** — the crabbox verb reference, which gains a `doctor` example and moves its
`stdout:` matcher from `0.51.0` to `0.78.0` — and **`.gitignore`**, which gains four entries this cutover needs: `.check/` (a check run's scratch tree), `.containerignore` and `.dockerignore` (the ignored halves of an image build), and `image/`.

**The two removed steps, and why removing them is the honest fix rather than a loss of coverage.** Both declared a
`stdout:` matcher and both failed with the same stderr:

```
crabbox: doctor: exit=1, want 0 (stderr: crabbox doctor exited 1: doctor found problems)
```

`crabbox doctor` exits 1 whenever it "found problems", and a credential-free pod has unready prerequisites by
construction - so the assertion measured the venue, not this change. The plugin's `invokeCLI` states the contract
it is bound by: "The CLI's exit code is the verdict signal; a non-zero exit is reported as a runErr" - so the
declared `stdout:` matcher is never consulted. **The passthrough is instead proven by four pieces, all measured:**

1. **the passing on-venue step above** - the provider catalogue is reachable through the verb and the `firecracker:`
   firecracker block is accepted by the input schema at all — it could not be parsed before this change — while the flags correctly do NOT reach the CLI, because providers defines no --provider/--firecracker-*: that is the negative boundary the unit test asserts;
2. **the argv unit tests** - `doctor --target linux` -> `--target linux`; `doctor --firecracker-binary firecracker` ->
   `--firecracker-binary firecracker`; `providers` -> neither;
3. **in-venue measurement of the CLI's own flag surface** - `crabbox providers --provider firecracker` and
   `--firecracker-binary firecracker` both exit 2 with `flag provided but not defined`; `crabbox doctor` documents
   `--provider` and accepts `--firecracker-*`;
4. **the removed steps' own stderr** above, which is a property of the venue.

The exit-vs-matcher precedence is a shared verdict-pipeline question and is filed - see the Filed issues section.
